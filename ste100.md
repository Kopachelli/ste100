# ste100 — project brief

Read this before doing work in this repository.

## What this repository is

Four things that make ASD-STE100 Simplified Technical English usable inside
Claude Code, plus one proposal to the standard itself.

| Component | Path | What it is |
|---|---|---|
| **Skill** | `skills/ste100/` | The knowledge and the checker. Rules, word counting, text types, examples. |
| **Command** | `.claude/commands/ste100.md` | `/ste100` — run a check or a rewrite on a target, now. |
| **Agent** | `.claude/agents/ste100.md` | `ste100` — an autonomous documentation agent with memory. |
| **Proposal** | `.change-proposals/` | A filled ASD change form, drafted and not sent. |

ASD-STE100 is a controlled natural language written by the aerospace and defence
industry. Part 1 is 53 writing rules in nine sections. Part 2 is a dictionary of
875 approved words and 1274 words that are not approved. This project implements
part 1. It does not contain part 2.

## Two hard rules

Everything else here is a preference. These two are not.

### 1. No ASD material enters this repository

`.input/` is gitignored in full and must stay that way. It holds ASD-STE100
Issue 9, the blank change form, and the STEMG white paper.

ASD-STE100 is free to obtain and **not free to redistribute**. Issue 9 permits
reproduction only with the written authority of an officer of ASD, or by eight
listed categories of organization that this project does not belong to.

That means:

- No dictionary content, ever — not the approved words, not the alternatives,
  not the list of recurring errors.
- No verbatim rule text. Cite the rule **number** and paraphrase.
- No filled change form as a committed file. `.docx` and `.pdf` under
  `.change-proposals/` are gitignored; `fill_form.py` regenerates them locally.
- Examples in this repository are written from scratch, including examples that
  illustrate a rule the standard also illustrates.

Before any commit:

```bash
git ls-files | grep -cE '^\.input/|\.docx$|\.pdf$'   # must print 0
```

Refer to [NOTICE.md](NOTICE.md).

### 2. Never claim STE compliance

Rules **1.1, 1.2, 1.3, 1.4, 1.6 and 9.2** are defined by the approved dictionary
in part 2. This project does not have it and cannot check them.

Say: *"This text obeys the structural rules of ASD-STE100. Word choice was not
checked against the approved dictionary."*

Never say: *"This text is STE compliant."*

The word to use is **STE-informed**. A maintenance organization that ships a
manual believing it is compliant, when the vocabulary was never checked, has a
real problem. This is not pedantry.

## The checker

`skills/ste100/scripts/ste_check.py`. Standard library only.

```bash
python skills/ste100/scripts/ste_check.py --type auto FILE
python skills/ste100/scripts/ste_check.py --type procedure --glossary g.json FILE
cat text.md | python skills/ste100/scripts/ste_check.py -
python skills/ste100/scripts/test_ste_check.py     # must pass before any commit
```

Findings are `VIOLATION` (certain) or `review` (heuristic). Each carries its rule
number. Exit code 1 when there is at least one violation.

**Always run it. Never count words by eye.** Section 8 of the standard defines
what a word is, and an STE count differs from a plain count in both directions.
`Refer to Testing and Fault Isolation, page block 1001.` is six STE words, not
nine.

The test suite asserts 39 word counts against numbers the standard publishes for
its own examples. If you change the counting logic and one stops matching, the
logic is wrong, not the test.

## Classify the text before applying anything

STE is not one rule set. This is the mistake that matters most.

| Type | Limit | Verb form |
|---|---|---|
| Procedure | 20 words (5.1) | Imperative (5.3) |
| Description | 25 words (6.3) | No imperative |
| Safety instruction | 20 words (5.1) | Command or condition first (7.2) |
| Note | 25 words (5.5) | Information only, no requirement |
| Machine-facing string | 25 words | Follow the sense of the string |

Classify each block, not the whole document.

## Memory

The agent keeps two stores, split by who the knowledge belongs to.

| Store | Where | Committed | Holds |
|---|---|---|---|
| **Project** | `.ste100/memory/` | Yes | Terminology rulings, scope decisions, audit history |
| **User** | agent memory (`memory: user`) | No | Preferences, corrections, working style |

Project memory is committed on purpose. STE prescribes a company terminology
database, and a terminology decision belongs to the project and its team, not to
the person who happened to make it. User memory is private and travels with the
person across projects.

Both use the same format: one fact per file, frontmatter with `name`,
`description` and `metadata.type`, and a one-line pointer in the store's
`MEMORY.md` index. Link related facts with `[[slug]]`.

## Conventions

- Work on `dev`. `main` takes merges, not direct commits.
- `python skills/ste100/scripts/test_ste_check.py` passes before every commit.
- The leak check above prints `0` before every commit.
- A proposal to the STEMG is written in STE and checked with our own tool.
- Nothing is sent to `stemg@asd-ste100.org` without the author saying so.
